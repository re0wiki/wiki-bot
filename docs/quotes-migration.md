## 技术约束与风险

- **性能约束的实测结论（2026-08-09，4 倍规模模拟）**：Lua 侧远未触限（4x 数据 require+扫描 CPU 仅 0.4s，Scribunto 限 10s）；`frame:preprocess` 贡献仅 ~10% 且**不可去**（无 preprocess 时 `<ref>` 变字面文本、`{{Seirei}}` 等模板不展开）。**真正的硬约束是 MediaWiki post-expand include size 2MB 上限**（与页面源码 2048KB 上限同为 2MiB，对同一数据量级触发）：当前全量输出 1.1MB，4 倍后 ~4.4MB → 输出被整体丢弃（仅剩警告链接）。对策已定（2026-08-09 用户裁决）：`table=` 参数已上线（按名懒加载单表，向后兼容逐字节验证），`/all` 页届时拆为**动态子页**（每页 1-3 次 `query|table=` 调用，各自独立 2MB 预算），不引入 bot 编译层——静态编译不推高容量墙（编译产物同样撞 2048KB 源码限），且语录数据改动不频繁、一次性检查即可，无需常驻巡检。拆分粒度按表/按季等有逻辑的单位（如实况解说按季拆子表）。**/all 拆页已实施（2026-08-10，P2 上线后全量 3.49MB 撞墙）**：6 个动态分表页（角色 872KB / 早期ask 401KB / 实况旧版 771KB / 新编+OVA 477KB / 第二季 723KB / 其他 80KB，均为渲染后 HTML 实测），/all 改索引；分组留了 P3/P4 余量（早期ask 独占页——全量后 ~1.6MB；角色页 P6 英译回填后 ~1.1MB）；空占位表（帕克/福尔图娜/Web评论）不上分表页（避免空结果提示与分类污染），有内容后加回。当日曾短暂上线静态编译试点（re0_quotes_all + jobs quotes-all + /all 静态化）并已整体撤销
- **Fandom 上传**：允许 mp3 ✓、**xlsx ✗**；文件大小限制待实测（88MB mp3 可能超限，备选 archive.org 托管 + wiki 外链）；xlsx 类原档归宿已定（2026-08-09 用户手动归档至 OneDrive `文档\杂项\re0\长月qa原档备份`，re0-corpus 与 wiki 均不适合 xlsx）
- **译名一致性**：LLM prompt **注入 ja→zh 专有名词表**（2026-08-09 用户裁决，反转当天早些时候的「不注入」决定）：目的不是规定用字，而是让弱模型**识别专有名词**、不把角色名当普通名词（试点 v1 曾把 パック 译成「包包」）。表由 `logs/p0_build_name_table.py` 从 zh 站角色页 infobox（name/name_ja_kanji/name_ja_kana，跟随重定向，短名取首段）抓取 + 手工补充段（术语/昵称/俗语）生成 → `logs/name_table_ja2zh.json`（90 条）；表只收 Re:Zero 作品内专有名词与相关人物——**一般世界知识不收**（かぐや様=辉夜大小姐、ドラえもん、鳳凰院凶真 等其他作品要素靠译名表补不全，2026-08-09 用户裁决）；infobox name 字段偏全名且个别繁体，短名以译名表标准为准（菲莉丝/艾尔莎/罗姆爷）。昵称惯例按 infobox 严格区分：**ベア子=贝亚子、ベティ=贝蒂**（试点曾错误归一，已回改）。本地归一（translation fix 规则）仍保留作兜底（注入后 v2 仍漏了 1 处 贝阿特丽丝被兜底抓住）；`fix:translation` 的 generator 不覆盖 Module 命名空间是**有意为之**，确证时用 `-simulate` 手动指定子表。**若注入后质量仍不达标就换模型，不让另一模型全量检查**（かぐや様 类低频词处理不好时全检失去意义）
